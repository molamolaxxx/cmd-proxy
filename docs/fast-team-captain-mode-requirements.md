# Fast Team 队长模式需求说明

> 文档状态：需求草案，待评审
> 编写日期：2026-09-06
> 适用范围：cmd-proxy、Starweave ConfigUI、MolaChat、Fast Team、TalkTo、外部信道、Starweave Task

## 1. 背景

当前 Fast Team 采用全员互通模式：每个成员都能看到其他成员的名称、职责描述和路由信息，也可以通过 `talk_to` 与队内任意其他成员通信。

该模式适合成员之间自由协作，但团队规模增大后容易出现以下问题：

- 每位成员都能自主发起横向沟通，消息链路和协作关系容易失控；
- 成员可能重复派发工作、相互确认或形成循环通信，增加上下文与调用成本；
- 所有成员都暴露给外部信道或任务分配入口时，用户难以判断实际负责人；
- 团队缺少唯一协调者，职责边界不清晰。

因此，需要在保留现有行为的基础上，为 Fast Team 新增“队长模式”。队长模式采用星形协作结构：队长是团队唯一协调入口，队长可以联系所有队员，普通队员只能联系队长。

## 2. 目标

本需求需要实现以下目标：

1. Fast Team 支持“普通模式”和“队长模式”两种团队模式。
2. 普通模式完整保留当前的全员互通行为及既有配置兼容性。
3. 队长模式下，一个团队有且仅有一名队长，并且创建团队时必须由用户手动指定。
4. 队长能感知自己的队长身份、全部队员及其职责，并能联系所有队员。
5. 普通队员能感知自己处于队长模式、知道队长是谁及其职责，但不能看到或联系其他普通队员。
6. 通信限制必须同时由系统提示词和服务端路由强制执行，不能只依赖模型遵守提示词。
7. Starweave 和 MolaChat 的团队创建入口都允许用户选择团队模式并指定队长。
8. Starweave 和 MolaChat 产品内的团队会话均展示完整成员列表，用户可以直接选择任意成员并发送文字或附件；该交互不属于 Agent 的 `talk_to` 或外部业务入口。
9. 队长模式团队接入企微等外部信道时，只能由队长承接消息；不允许随机路由、Hash/亲和路由或指定普通队员。
10. Starweave Task 或其他任务派发能力以队长模式团队为目标时，只能把任务派发给队长。

## 3. 非目标

本期不包含以下内容：

- 不改变普通模式的成员可见性、`talk_to` 权限、信道路由或任务分配能力；
- 不支持一个团队配置多名队长、副队长或分层组织结构；
- 不支持在团队运行期间动态更换队长；如需更换，应删除并重新创建团队；
- 不把成员备注中的“队长”“负责人”等自然语言作为权限依据；队长身份必须来自结构化配置；
- 不允许模型通过普通联系人、全局 Agent 名称、`robotName`、`chatterId` 或其他路由机制绕过队内拓扑；
- 不改变子 Agent、定时任务、记忆等非队内通信能力的既有语义，但这些能力不得被用作绕过队长模式消息路由的通道；
- 不在本需求中引入队长自动选举、故障转移或队长不可用时自动切换成员。

## 4. 名词与模式定义

### 4.1 普通模式（Normal）

普通模式即当前 Fast Team 行为：

- 每个成员可以看到自己和其他全部队员的团队身份与职责描述；
- 每个成员可以通过 `talk_to` 联系其他任意队员；
- 外部信道与任务派发继续支持当前已有的成员选择策略；
- 未携带团队模式字段的历史数据和旧版创建请求一律按普通模式处理。

建议协议值：`NORMAL`。

### 4.2 队长模式（Captain）

队长模式采用唯一队长和多个普通队员组成的星形拓扑：

```text
                ┌────────┐
                │  队员 A │
                └───┬────┘
                    │
┌────────┐      ┌───▼────┐      ┌────────┐
│  队员 B │◄────►│  队长   │◄────►│  队员 C │
└────────┘      └────────┘      └────────┘

队员 A、B、C 之间不可直接发现或通信。
```

建议协议值：`CAPTAIN`。

## 5. 核心业务规则

### 5.1 团队创建

1. 创建 Fast Team 时必须选择团队模式。
2. 默认选择普通模式，以保持现有用户习惯和兼容性。
3. 选择普通模式时，不展示队长选择项，也不要求提交队长。
4. 选择队长模式时，必须从本次已选团队成员中手动指定一名队长。
5. 队长模式至少应包含两名成员，即一名队长和至少一名普通队员。若产品希望允许单人团队，应在评审时单独确认；本草案默认拒绝单人队长团队，因为其不具备团队协作意义。
6. 队长必须是团队全局成员表中的唯一成员，不能使用显示名称或备注代替稳定的 `teamMemberId`。
7. 服务端必须校验队长存在于成员列表中，且只能有一个队长。缺失、重复、无效或不属于该团队的队长标识均应拒绝创建。
8. 团队模式和队长身份创建后保持不可变。团队恢复、重启、跨实例重连时必须使用持久化值恢复，不得重新推断。

### 5.2 队内可见性

普通模式保持当前全员可见行为。

队长模式下：

| 当前身份 | 可看到自己 | 可看到队长 | 可看到其他普通队员 |
|---|---:|---:|---:|
| 队长 | 是 | 自己即队长 | 是，包含名称和团队职责备注 |
| 普通队员 | 是 | 是，包含名称、稳定路由目标和团队职责备注 | 否 |

补充要求：

- 当前成员自己的团队备注仍应作为身份与职责注入，但自己不能出现在可路由联系人列表中；
- 普通队员的提示词、工具上下文、联系人卡片和其他面向模型的投影中，不得泄露其他普通队员的名称、备注、`teamMemberId`、`acpClientId` 或数量明细；
- 管理端为了运维展示完整团队成员列表不属于模型可见性，但普通队员的 ACP 上下文不得因此获得完整列表；
- 混合团队或跨实例 fragment 也必须基于同一份全局 roster 和唯一队长身份裁剪成员视图，不能只按本地成员列表判断角色。

### 5.3 队内通信权限

普通模式保持当前任意成员到任意其他成员的通信能力。

队长模式的允许矩阵如下：

| 发送方 | 目标为队长 | 目标为普通队员 |
|---|---:|---:|
| 队长 | 不允许向自己发送 | 允许 |
| 普通队员 | 允许 | 不允许，包括向自己和其他普通队员发送 |

限制必须在两层同时落实：

1. **提示词层**：只向当前成员展示其允许联系的队内联系人，并明确说明角色与限制。
2. **服务端层**：`TeamTalkToDispatcher` 或等价权威路由层根据团队模式、发送方 `teamMemberId` 和目标 `teamMemberId` 校验通信边；禁止依赖提示词、显示名称或前端过滤作为安全边界。

当请求违反队长模式时，系统应明确拒绝，返回稳定的权限错误码和可理解的错误信息；不得静默改投队长、降级到普通 TalkTo、全局联系人或跨 Chatter 路由。

建议错误码：`TEAM_COMMUNICATION_FORBIDDEN`。

### 5.4 系统提示词与角色感知

队长的 Team harness 至少应表达：

- 当前处于哪个 Fast Team；
- 当前团队使用队长模式；
- 当前成员是该团队唯一队长；
- 队长负责协调、拆分、派发、汇总工作，并可联系所有普通队员；
- 展示所有普通队员的准确 `target`、显示名称和团队职责备注；
- 不得对自己调用 `talk_to`。

普通队员的 Team harness 至少应表达：

- 当前处于哪个 Fast Team；
- 当前团队使用队长模式；
- 当前成员是普通队员；
- 明确展示队长是谁、队长的准确 `target` 和团队职责备注；
- 队内消息只能发送给队长；
- 不展示、不猜测也不尝试联系其他普通队员；
- 不得对自己调用 `talk_to`。

成员备注继续遵循现有解析规则：用户填写的团队备注优先，未填写时使用能力说明或签名作为隐藏回退。队长角色来自结构化字段，不能要求用户必须在备注里填写“队长”。

### 5.5 外部信道

本节适用于企微及后续其他可以绑定 Fast Team 成员的外部信道。

1. 普通模式保持现有行为，可继续使用指定成员、随机选择和会话亲和/Hash 分配等策略。
2. 队长模式下，团队对外只暴露队长作为业务处理入口。
3. 用户选择队长模式团队后，界面应自动显示并锁定队长，不再提供以下选项：
   - 指定其他普通队员；
   - 随机选择成员；
   - 按单聊 `userId` 或群聊 `chatId` 进行亲和/Hash 分配；
   - 队长不可用时自动切换其他成员。
4. 持久化配置必须等价于 `FIXED + captainMemberId`。可以在存储层继续复用固定成员模型，但不能只靠前端自动填值。
5. 服务端保存配置、热重载、运行时解析和消息投递时都要重新校验：目标团队仍为队长模式且固定成员仍是该团队队长。
6. 队长不可用、团队未就绪或协调器断开时，消息应按现有失败/排队契约显式处理，不能转投普通队员。
7. 只有队长可以获得绑定外部信道的联系人或回复能力；普通队员的 Team harness 不得注入这些外部信道 target，也不得借此绕过队长通信拓扑。

建议新增错误码：

- `CAPTAIN_REQUIRED`：队长模式缺少有效队长；
- `CAPTAIN_ONLY_BINDING`：外部信道试图绑定到非队长成员或使用自动成员选择策略。

### 5.6 任务派发

本节适用于 Starweave Task、对外任务 API 及后续所有以 Fast Team 为目标的任务入口。

1. 普通模式团队继续支持现有 `FIXED`、`RANDOM` 和 `AFFINITY` 分配策略。
2. 队长模式团队作为任务目标时，实际 assignee 必须是队长。
3. UI 选择队长模式团队后，应隐藏或禁用成员分配策略，显示“由队长统一接收”，并把队长作为只读目标。
4. 请求协议应提交或规范化为 `FIXED + captainMemberId`。
5. 服务端目标解析器和任务服务必须拒绝以下请求：
   - `RANDOM`；
   - `AFFINITY`；
   - `FIXED` 但 `teamMemberId` 不是队长；
   - 未指定成员且无法从权威团队定义解析出队长。
6. 禁止服务端从队长备注、成员顺序或列表第一项推断队长。
7. 队长收到任务后，可以通过队内 `talk_to` 自主拆分并协调普通队员；任务系统仍只记录队长为正式 assignee，除非未来另行设计子任务委派模型。
8. 队长不可用时，任务应保持未派发、失败或按既有重试语义处理，不能自动降级到其他队员。

建议错误码：`CAPTAIN_ONLY_TASK_TARGET`。

### 5.7 用户直接进入团队会话

1. 普通模式和队长模式都保持当前可选择任意成员并进入其独立会话的交互。
2. Starweave 和 MolaChat 必须展示权威 roster 中的全部成员；队长可作为默认打开成员，但普通成员不得因此变成只读或被隐藏。
3. 产品内用户可以向任意 READY 成员发送文字和附件，仍须通过现有 owner、team、member、placement、session 与状态校验。
4. 本节的产品内直接会话不属于 Agent 的 `talk_to`，也不属于企微等 channel、任务、定时任务或外部任务 API；后两类入口仍分别遵守 5.4、5.5 和 5.6 的队长限制。

## 6. 数据与协议要求

### 6.1 建议字段

在团队创建请求和权威 `TeamDefinition` 中增加：

| 字段 | 类型 | 必填规则 | 含义 |
|---|---|---|---|
| `mode` | string | 新请求建议必填；旧请求缺省为 `NORMAL` | `NORMAL` 或 `CAPTAIN` |
| `captainTeamMemberId` | string/null | `CAPTAIN` 必填，`NORMAL` 必须为空 | 唯一队长的稳定 `teamMemberId` |

示例：

```json
{
  "schemaVersion": "1",
  "requestId": "req-01",
  "teamId": "team-01",
  "ownerChatterId": "owner-01",
  "name": "交付团队",
  "mode": "CAPTAIN",
  "captainTeamMemberId": "member-01",
  "members": [
    {
      "teamMemberId": "member-01",
      "sourceGroupId": "group-a",
      "sourceRobotId": "robot-a",
      "order": 0,
      "remark": "负责协调、派发和最终交付"
    },
    {
      "teamMemberId": "member-02",
      "sourceGroupId": "group-b",
      "sourceRobotId": "robot-b",
      "order": 1,
      "remark": "负责后端实现"
    }
  ]
}
```

### 6.2 权威性与投影

- `mode` 和 `captainTeamMemberId` 必须由 Team 权威定义持久化；
- list/get、团队事件、Starweave REST、MolaChat RPC 投影、跨实例协调协议和重启恢复都必须携带这两个字段；
- MolaChat 和 ConfigUI 保存的是投影或配置草稿，不能覆盖 cmd-proxy 的权威团队定义；
- 混合团队的协调器必须保存全局唯一队长，并将相同值投影到各参与实例的 fragment；
- 参与实例不能因为本地 fragment 不包含队长就退化为普通模式或允许本地成员互通；
- `teamMemberId` 是权限判断依据；显示名称、成员顺序、来源 Robot 名称和备注只用于展示。

### 6.3 幂等与兼容

- 同一 `requestId` 重放时，模式和队长不同应视为幂等冲突；
- 历史团队定义缺失 `mode` 时按 `NORMAL` 读取；
- 历史普通模式信道绑定、任务配置和团队行为保持不变；
- 新版服务端必须拒绝未知模式，不能把未知值静默当作普通模式；
- 如果采用现有 `schemaVersion=1` 的增量兼容方式，应保证旧调用方不传新字段时行为不变；是否升级 schemaVersion 由技术设计阶段结合 MolaChat 协议兼容性决定。

## 7. 交互要求

### 7.1 Starweave 创建团队

Starweave 的“创建团队”弹窗增加“团队模式”选择：

- 普通模式：说明“成员之间可以相互查看并直接通信”；
- 队长模式：说明“队长可联系所有队员，普通队员只能联系队长；外部信道和任务仅由队长承接”。

选择队长模式后：

- 在已选成员列表中为每位成员提供单选按钮或“设为队长”操作；
- 必须由用户主动选择，不默认使用第一名成员；
- 未选择队长时禁用创建或在提交时给出明确校验提示；
- 取消选择某成员时，如果该成员是队长，应清空队长并要求重新选择；
- 每个成员原有的独立团队备注输入保持不变，备注状态继续按稳定成员来源身份保存；
- 多成员和移动端场景下，模式、队长选择和备注区域必须可滚动、可操作且不互相遮挡。

### 7.2 MolaChat 创建团队

MolaChat 的 Fast Team 创建入口需要提供与 Starweave 一致的模式和队长选择能力：

- 使用相同的 `NORMAL` / `CAPTAIN` 语义；
- 队长只能从已选成员中选择且必须手动指定；
- 创建请求携带结构化模式和队长成员 ID；
- 普通模式仍生成原有全员 roster；
- 队长模式仍可保存完整权威 roster，但各成员获得的可见联系人必须按角色裁剪；
- 本地团队与可信协调器创建的混合团队使用同一套规则。

### 7.3 团队列表与详情

- 团队卡片或详情应显示“普通模式”或“队长模式”标识；
- 队长模式应清晰标出唯一队长；
- 队长不可用时应显示其真实状态，不自动把其他成员标为临时队长；
- 团队恢复或跨实例状态尚未对齐时，如果无法确认权威队长，相关信道和任务操作应暂不可用并给出原因。

### 7.4 信道与任务配置

- 在企微信道配置中选择队长模式团队后，成员选择区显示队长并锁定，隐藏 `RANDOM` 和 `AFFINITY`；
- 在任务创建、任务 API 配置中选择队长模式团队后，成员分配显示为“固定：队长”；
- 前端切换团队时必须重新读取该团队模式和队长，不能沿用上一个团队的成员选择值；
- 前端限制只用于交互引导，所有约束仍需服务端校验。

## 8. 权限与安全边界

1. 权限判断必须使用 Team 权威定义中的 `mode`、`captainTeamMemberId`、发送方和目标 `teamMemberId`。
2. Team harness 中的联系人裁剪不能替代路由校验。
3. 队员不得通过来源 Robot 的普通 contacts、全局 registry、外部联系人、远程 TalkTo 或构造 `acpClientId` 绕过限制。
4. 跨实例队长模式通信必须由可信协调器校验全局 roster、队长身份、成员 placement 和 transport；不得信任请求自报身份。
5. 协调器离线时，混合团队保持 fail-closed，不得降级为本地普通团队。
6. 队长模式不应把其他普通队员的身份信息注入普通队员的上下文、日志卡片或工具描述；管理端审计事件可保留必要身份，但需遵循既有授权边界。
7. 配置热重载、团队恢复和旧事件重放不能短暂开放全员互通；在模式和队长未确认前应拒绝队内发送。

## 9. 状态与异常处理

| 场景 | 预期行为 |
|---|---|
| 创建队长模式但未指定队长 | 拒绝创建，提示必须手动指定一名队长 |
| 指定的队长不在成员列表 | 服务端拒绝创建 |
| 普通模式请求携带队长 ID | 拒绝请求或要求调用方清空，避免歧义 |
| 队员尝试联系另一名队员 | 服务端明确拒绝，不转发、不唤醒目标 |
| 外部信道配置为随机或亲和路由 | 拒绝保存或拒绝生效 |
| 外部信道绑定到普通队员 | 拒绝保存或拒绝生效 |
| 任务目标是随机、亲和或普通队员 | 拒绝创建/派发，返回稳定错误码 |
| 队长 BUSY | 沿既有队长 inbox、排队或忙碌语义处理，不改投队员 |
| 队长 ERROR/CLOSED | 显式失败或等待恢复，不自动选举 |
| 混合团队协调器不可用 | 队内跨实例通信、信道和任务路由安全失败 |
| 历史团队没有模式字段 | 作为普通模式恢复 |

## 10. 验收标准

### 10.1 创建与持久化

- Starweave 和 MolaChat 均可创建普通模式与队长模式团队；
- 队长模式没有手动指定队长时无法创建；
- 一个队长模式团队只能有一个队长；
- 重启 cmd-proxy、重连 MolaChat 或恢复混合团队后，模式和队长保持不变；
- 历史团队无需迁移即可继续按普通模式工作。

### 10.2 提示词与可见性

- 队长明确感知自己是队长，并看到全部普通队员及其职责；
- 每名普通队员明确知道谁是队长，只看到队长和自己的身份信息；
- 普通队员上下文中不存在其他普通队员的路由 ID、名称或备注；
- 成员自己的显式团队备注正常注入，且不把自己列为可路由联系人。

### 10.3 TalkTo 路由

- 队长可以分别向所有普通队员发送消息；
- 普通队员可以向队长发送消息；
- 普通队员使用已知旧 ID、显示名称、`acpClientId` 或其他路由方式联系普通队员时均被拒绝；
- 非法请求不进入目标 inbox、不产生目标 Agent turn，也不降级到普通 TalkTo；
- 普通模式的全员互通回归通过。

### 10.4 外部信道

- 企微选择普通模式团队时，原有固定、随机、亲和/Hash 路由均可继续配置；
- 企微选择队长模式团队时，只显示并绑定队长；
- 通过配置文件或旧客户端提交随机、亲和或非队长绑定时，服务端拒绝；
- 队长不可用时不会把消息发送给普通队员；
- 普通队员不会获得外部信道联系人或回复 target。

### 10.5 任务派发

- UI 选择队长模式团队后，任务目标自动且只读地指向队长；
- REST/MCP/对外任务 API 直接提交 `RANDOM`、`AFFINITY` 或非队长成员时均被拒绝；
- 最终任务 assignee 始终记录为队长；
- 队长不可用时不会选择其他队员；
- 普通模式团队原有三种任务分配策略回归通过。

### 10.6 本地与混合团队

- 本地 Starweave Team、本地 MolaChat Team 均满足同一权限矩阵；
- 可信协调器创建的混合团队在队长位于本地或远端两种情况下均满足同一权限矩阵；
- 本地 fragment 不包含队长时，普通队员仍只能通过协调器联系全局队长，不能看到或联系其他本地队员；
- 协调器中断时不发生权限降级。

## 11. 建议测试范围

实现阶段至少覆盖以下自动化与实测：

- `TeamDefinition` / 创建命令的模式、唯一队长、兼容与幂等校验；
- `TeamTalkToContextInjector` 对普通模式、队长、普通队员的联系人裁剪；
- `TeamTalkToDispatcher` 的完整通信矩阵及绕过尝试；
- 本地团队和混合团队的 global roster / fragment 队长投影；
- Starweave 创建弹窗、团队列表、团队会话入口；
- MolaChat 创建入口及团队会话入口；
- 企微信道配置、配置文件校验、热重载、固定投递、队长不可用；
- Starweave Task UI、REST、MCP 和对外任务 API 的目标校验；
- cmd-proxy 重启、MolaChat 重连、团队恢复和协调器断线场景；
- 现有普通模式 Fast Team、TalkTo、企微随机/亲和路由和任务三种分配策略的回归。

业务验收需要分别实测 Starweave 与 MolaChat，并覆盖本地团队和混合团队。实时展示与重新进入会话后的历史恢复应保持一致，且不得出现重复 TalkTo、任务或工具卡片。

## 12. 待评审确认项

以下问题不影响本需求主体，但应在进入技术设计或开发前确认：

1. 是否允许只有一名队长、没有普通队员的单人队长团队；本草案默认不允许。
2. 管理员在 Starweave 团队详情中是否保留普通队员会话的只读查看能力；本草案允许只读，但禁止直接发送业务消息。
3. 队长 BUSY 时，外部信道和任务统一采用“排队”还是“明确忙碌失败”；本草案要求沿各入口既有语义，但绝不切换成员。
4. 本期是否要求为既有普通团队提供“重建为队长模式”的快捷操作；本草案只支持新建时选择，不支持原地转换。
5. 协议继续使用 additive `schemaVersion=1`，还是因 MolaChat 联动升级版本；本草案不预设结论。
